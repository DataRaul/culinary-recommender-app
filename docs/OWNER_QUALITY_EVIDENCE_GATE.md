# Owner feedback and PR evidence gate

Status: installed as a bounded Culinary workflow improvement. This is a governance/CI capability, **not** a recipe/runtime change.

## Enforcement

- New PRs created from **2026-10-16 00:00 UTC** onward must publish exactly one complete frozen package packet and its Supporter, Critic and synthesis sidecars. Earlier PRs (including #428 and #429) are grandfathered; this is explicit, not a new waiver for their other gates.
- The `Quality evidence — reviewed packages / quality-evidence` check runs with `pull_request_target` using only trusted **base-branch scripts** and read-only candidate data. No contributor PR code is executed. The shared Agent OS checker is fetched by immutable commit, then verified against trusted SHA-256 pins.
- It fails closed for missing packet/reports/contract, stale base, extra changed files, incomplete material finding dispositions, wrong review mode or corrupted hashes. No reviewer verdict is generated by CI.
- **A green check is not intrinsically non-bypassable.** To block GitHub UI merges, repository branch rules must require the `quality-evidence` status check. This must be configured and verified separately by an authorized admin; the current tool path does not change branch rules. Until then, the existing coordinator obligation to run checks before merging remains controlling.
- The new workflow creates **no scheduled Actions**, API subscriptions or database writes. It adds one lightweight PR job for new PR events; the first run after publication must confirm actual installation behavior.
- A baseline PR advanced by other writers must be reconciled and refrozen. The gate does not silently adjust the base, reset budgets or accept review sidecars generated against older candidate bytes.
- This pilot restricts **new PRs**, not already-open historical work and not direct pushes by admins. For a truly non-bypassable gate, configure required checks and branch restrictions externally.

## Owner-facing result

Run `node scripts/owner-quality-report.mjs <checkout-root> <packet-relative-path>` after actual Supporter, Critic and synthesis reports have been written. The same template runs in GitHub's PR job summary for passing new packages. ChatGPT's coordinator must give the owner the short result **in chat** at the normal terminal boundary, without requiring a link, download or manual inspection:

- what changed and why it matters to the product;
- Aligner / Builder / Supporter / Critic / Synthesis outcomes;
- material failures resolved, deferred or still blocking;
- whether CI, merge, deployment and lane checkpoint were actually verified;
- owner action (none versus a specific decision) and the next handover.

Do not claim that a reviewer is independent in same-chat mode, that a CI PASS equals a merge or that automated checks prove semantic truth. Do not confuse a package's business value with the number of reports or tests.

## Installation and roadmap verification order

Before merging installation, require current authorized same-chat reviews, the actual pinned checker on the exact outgoing inventory, and exact-head required CI. The contract already names the first live PR trigger as a **post-merge** dependency: a workflow absent from main cannot prove its own installed trigger before installation. This sequencing does not mark live activation as passed.

After installation, verify the first real post-cutover event while delivering the next separately authorized roadmap package. Do not open a testing-only PR or restart owner-stopped acquisition to manufacture an event. Retain operational activation as OPEN until the actual trusted-base job executes; report any failure and keep the affected package unmerged. Required branch-check enforcement remains a separate administrator-controlled fact; report protected:false or unavailable administration access honestly, without claiming hard enforcement.

Owner steering 2026-10-15: evaluate review usefulness during normal roadmap delivery. Record real findings, repairs and effort within those packages; this is not a comparative reliability experiment and adds no paid service or scheduled workflow.
