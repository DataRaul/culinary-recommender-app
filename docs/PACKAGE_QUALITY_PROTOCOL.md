# Package quality protocol — owner-selected pilot V1

Status: PROCEDURAL_PILOT; owner-selected `SAME_CHAT_SEQUENTIAL` (2026-10-14). Apply to every substantive bounded package in this project. Read the root AGENTS instructions, existing contracts and `config/package_quality_adapter.json`. Fetch the shared skill, role references and checker from the exact public source commit in that adapter; verify file hashes before execution. A connector can materialize those exact files; a local checkout can supply `--agent-os-root`. Never fetch floating main for execution or install a paid API/service. This is developer workflow only, outside application/notebook runtime.

## Normal cycle

1. **Align internally.** Reconcile live main/open PRs/checks, lane authority, latest user steering, versioned lane goal and checkpoint. Route through canonical KC `domains/project_execution/objects/agentic_work_mandate_harness.md`; the canonical conversation router retains optional post-task coaching. Retrieve known context before asking. A clear request or continue needs no ritual question.
2. **Record a package contract.** Copy `docs/package_quality/CONTRACT_TEMPLATE.json` into a new named contract and fill it from evidence. Use the existing lane goal if sufficient; otherwise record a small versioned goal under `docs/package_quality/goals/<lane>/vN.json`. The supplied quality-pilot goal covers installation only, not other research/product goals. Preserve authorized outcome, why, acceptance IDs, fixed constraints, source/time and goal revisions. Examples are not universal requirements.
3. **Build/check.** Keep one bounded outcome. Record criterion → deliverable → evidence → contribution. Recheck alignment after material discoveries. Scope corrections are autonomous; new goals or frozen-criterion changes require existing authority. Preserve failures, remaining budget and blockers across continue/resume.
4. **Freeze.** Use the hash-pinned shared checker through the wrapper. Include every proposed publication change and generated deliverable plus evidence; in a real checkout use `--git-base` to include changed/untracked paths. Connector publishers use the exact outgoing Git tree entries, including deletions. Avoid circular hashes: packet and review reports are validated sidecars.
5. **Supporter pass in this chat.** After freeze, run the pinned `next` driver. Inspect the exact deliverables and acceptance evidence constructively and record applied Knowledge Core commit/object/rule provenance. Use the actual session identity, `review_mode: SAME_CHAT_SEQUENTIAL`, `independent: false`, `stage: 3` and frozen packet digest as predecessor. Require meaningful criterion evidence and findings; repairs require refreeze and full final-candidate rechecks within inherited budget.
6. **Critic and synthesis in this chat.** Invoke `next` for the Critic, challenge counterexamples, failure paths, contradictions, scope and acceptance criteria on the exact same candidate. Use stage 4 and the canonical Supporter digest as predecessor, without pretending blindness or independence. Invoke `next` for stage 5 synthesis: bind both canonical report digests, explain goal contribution, disposition **every** Supporter/Critic finding in order and set `next_gate: REQUIRED_CI`. Unresolved material defects HOLD publication.
7. **Validate before publication.** Invoke `next` until no stage remains, then `validate --synthesis` against exact outgoing paths and freshly read main/branch heads. Missing ordered stage, changed candidate/goal/adapter/evidence, stale base, unverified knowledge provenance, material findings or exhausted budget HOLD publication. Passing grants only `SEQUENTIALLY_REVIEWED_READY_FOR_REQUIRED_CI`, not merge/deployment acceptance. Proceed through existing authorized PR, required CI and eligible merge; preserve local gates.
8. **Checkpoint.** Store goal version/hash, last evidence, reports, unfinished criteria, failures, decisions, remaining budget and exact authorized next action. Reconcile and check the goal again on takeover. A handover is a locator/history record, never evidence of freshness or success.

## Invocation

```bash
python scripts/package_quality.py --agent-os-root /exact/pinned/agent-os freeze --contract docs/package_quality/contracts/<package>.json --paths <all-publication-changes> --output docs/package_quality/evidence/<package>/packet.json

python scripts/package_quality.py --agent-os-root /exact/pinned/agent-os validate --packet docs/package_quality/evidence/<package>/packet.json --supporter docs/package_quality/evidence/<package>/supporter.json --critic docs/package_quality/evidence/<package>/critic.json --synthesis docs/package_quality/evidence/<package>/synthesis.json --current-base <fresh-main-sha> --publication-list /scratch/outgoing-paths.json
```

The thin wrapper verifies each shared SHA-256 and forwards `next`, synthesis validation and existing `lane-prepare`/`lane-verify`; it does not launch reviewers, call APIs, publish, bypass CI or fetch production data. The active chat performs every returned review pass in sequence. Session identity, chronology and semantics are self-reported; hash links alone do not prove review quality or independence. No exclusive publisher/background hook is installed.

## User-visible behavior and cost

Use ordinary prompts. Alignment is usually internal; ask only for a consequential missing choice. During a package, give concise permitted progress updates. At terminal, report outcome, supporter/critic findings resolved or held, contribution, remaining gap and next gate; do not merely say PASS. New prompts reuse goal/state under current authority. Current chats must read updated root instructions before their next package; repository files cannot inject new instructions into already-running chats.

No new paid service, recurring API charge or scheduled Actions are required. Reviews consume the existing account allowance and extra time. Record unknown telemetry honestly and preserve existing budget limits. Historical installation reviewers remain historical independent sessions; new same-chat passes are expressly non-independent and baseline-versus-protocol reliability remains unmeasured.

## Same-chat activation and migration (2026-10-14)

The adapter selects `SAME_CHAT_SEQUENTIAL`; every new or migrated active contract must also select it explicitly. Legacy contracts without `review_mode` retain `INDEPENDENT_SESSIONS` until their owning lane migrates. The contract must place nonempty `stage_evidence.align` and `stage_evidence.build_qa` paths inside frozen `required_evidence`. Read the exact pinned `skills/package-quality-gate/references/sequential.md`. Execute alignment → build/QA → freeze → `next`/Supporter → `next`/Critic → `next`/synthesis → `next`/full validation **inside the active chat**. The same-chat reports use actual identity, `independent: false`, stages 3/4/5 and canonical predecessor/report digests; synthesis retains all findings and exact resolution evidence. No reviewer identities may be invented.

For existing packages, **do not rewrite historical contracts, reports or budgets**. Only the owning lane may migrate an active contract by preserving every acceptance criterion, source authority, remaining budget, goal and known failure, adding the selected mode and stage evidence, then refreezing. Old independent reports remain archives and do not count toward the new sequence. An earlier HOLD is not promoted automatically. Keep old versioned goal files intact; use a new revision if historic wording conflicts. Repairs reuse inherited fixed limits and must rerun both final-candidate passes and synthesis. Changing base, files, evidence or any report invalidates downstream stages.

Preserve Culinary's exactly-one-bounded-package rule: perform the three review stages within that package, then rotate **only** its registered lane CURRENT/PREVIOUS atomically on `continuity-state` with an expected-head lease and stop. Keep shared registry and other lanes intact. The current chat must load changed root instructions itself; there is no automatic injection into other chats, paid reviewer API, scheduled quality Action or background service. No recipe/corpus/search, authentication, recommendation, D1, runtime or Cloudflare change is implied. Existing independent-session consumers remain supported by the shared source.

## Owner-report and CI evidence enforcement (2026-10-15)

Apply `docs/OWNER_QUALITY_EVIDENCE_GATE.md` after this package is installed. For new PRs after the documented cutover, the read-only trusted-base `quality-evidence` check verifies exactly one pinned package review before GitHub merge. Existing PR428/429 remain outside this new check. The coordinator must still execute actual Supporter/Critic/synthesis; CI does not launch models. A green check is a procedural evidence result and does not replace full CI, merged-byte verification or the accepted app gate. Enforcement becomes non-bypassable only if the `quality-evidence` check is marked required by branch policy; otherwise an admin can merge despite failure.

At a terminal package boundary, **before the complete handover JSON**, send a compact business-owner result: what was achieved, usefulness to Culinary, Aligner/Builder/Supporter/Critic/Synthesis findings and repairs, CI/merge/deploy/acceptance truth, owner action and next gate. Generate it from actual reports via `scripts/owner-quality-report.mjs` when available, then add only verified post-review integration facts. No routine mid-stage narration is required. Missing review reports become HOLD, not a fabricated summary.
